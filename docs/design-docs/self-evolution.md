# Self-Evolution Design

## Objective

Let the agent improve over time without allowing it to silently rewrite its own
behavior in unsafe ways.

Self-evolution means proposing and tracking improvements to prompts, policies,
memory, fixtures, and docs. It does not mean unreviewed code or policy changes.

## Safe Improvement Loop

1. Run a task.
2. Record structured trace and audit events.
3. Detect failure, ambiguity, drift, or user correction.
4. Classify the cause.
5. Propose one improvement candidate.
6. Run regression evals, including frozen golden fixtures.
7. Require approval or an explicit acceptance rule.
8. Commit the accepted change with versioned artifacts.

## Phase 1 Requirement

The full improvement loop can wait, but append-only recording cannot. From the
first executable runtime, record enough information to reconstruct:

- user intent;
- model output;
- tool calls;
- policy decisions;
- observations;
- errors;
- improvement candidates;
- prompt, policy, memory, and schema-context versions.

## Milestone 7 Control Boundary

The first implementation is a control plane only:

- `agent_runtime.self_evolution` validates improvement candidates, memory
  records, rollback plans, drift fixtures, and acceptance-gate reports.
- The artifact manifest at `artifacts/artifact-manifest.v1.json` is the source
  for prompt, policy, memory, and eval versions recorded in traces.
- `artifacts/memory/runtime-memory.v1.json` records the closed-by-default
  runtime memory policy with source, author, confidence, evidence, scope,
  expiration, and review status.
- `artifacts/evals/drift/self-evolution-drift-v1.json` repeats stable
  database-analysis and workflow prompts and compares semantic signatures
  rather than volatile run ids. Database signatures include selected tables,
  query-plan dimensions, measures, assumptions, policy outcome, proposed SQL
  hash, result-explanation source, fixture id, and explanation hash.
- Acceptance remains closed unless the candidate is proposed, explicitly
  reviewed as approved, candidate provenance is reviewed as approved, frozen
  evals pass from `artifacts/evals/golden` with manifest artifact versions,
  drift checks pass, rollback covers every affected artifact path with matching
  artifact type and before/after versions, and behavior-shaping changes are
  limited to one artifact type at a time.
- Gate inputs must prove they came from the configured frozen fixtures. Eval
  results must include every fixture case from `artifacts/evals/golden` and
  the manifest `golden_fixture` version. Drift results must include the
  configured drift fixture id, path, file hash, and every drift case.

The module does not write prompt, policy, memory, eval, schema, or code
artifacts. It returns a blocked or passed gate report for a reviewed operator or
future workflow to act on.

## Guardrails

- Keep a frozen golden eval set. Do not edit it just to make a new change pass.
- Change prompt, policy, memory, or schema retrieval one at a time when possible.
- Make rollback cheap by versioning all behavior-shaping artifacts.
- Store memory with provenance: source, timestamp, author, confidence, and
  supporting evidence.
- Treat user corrections as candidates, not automatically trusted truth.
- Detect drift when repeated questions start producing materially different
  query plans or answers.
- Do not allow a candidate record to become an accepted behavior change solely
  because it was generated by the agent.
- Treat fixture rewrites as behavior-shaping changes; new fixture additions
  should still carry provenance and review state.

## Improvement Targets

- Prompt text and structured-output schemas.
- Query safety policy.
- Domain glossary entries.
- Schema retrieval ranking hints.
- Eval fixtures.
- Ambiguity handling rules.
- Result explanation templates.
